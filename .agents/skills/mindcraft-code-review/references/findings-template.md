# Findings Report Template

Use this exact structure for every report written by `mindcraft-code-review`. Consistency makes reports comparable across runs.

## Filename

```
docs/code-review/<YYYY>-<MM>-<DD>T<HH>-<MM>.md
```

UTC. `:` replaced with `-` so it's portable to Windows. Examples:
- `docs/code-review/2026-05-01T14-22.md`
- `docs/code-review/2026-05-01T09-04.md`

If `docs/code-review/` doesn't exist, create it. If creation fails, fall back to `tools/explorer/data/code-review-<timestamp>.md` and surface the fallback at the top of the terminal summary.

## Full report structure

````markdown
# Code review — <YYYY-MM-DD HH:MM UTC>

| Field | Value |
| ----- | ----- |
| Branch | `<branch-name>` |
| Mode | full \| branch |
| Files reviewed | <N> |
| Findings | <N> total · <N> major-revision · <N> small-fix |
| Hot-spots in scope | <N> of <total hot-spot files> |
| Reviewer | mindcraft-code-review skill |

## Project index (snapshot)

<one-paragraph version of the architecture, then a compact bullet list grouped by subsystem (Agent core / Prompter & models / Commands & objectives / Memory / Vision / Multi-bot). 5-15 lines total. Lift wording from references/mindcraft-architecture.md but don't paste the whole thing.>

## Hot-spots reviewed this run

<bulleted list of hot-spot entries that landed in scope. For each: name, file path, one-sentence reason. Skip entirely if no hot-spots were in scope.>

## Findings

<for each finding, render the finding template below. Findings are pre-ranked: major-revision before small-fix; within each tier, lower effort first; within ties, hot-spot files outrank others. IDs are F-001, F-002, ... in render order.>

### F-XXX — <title>

| Field | Value |
| ----- | ----- |
| Severity | **major-revision** \| small-fix |
| Type | bug-risk \| correctness \| design \| perf \| cost \| readability \| security \| architecture-drift |
| Effort | <30min \| 1-4h \| 1-2d \| >1wk |
| Where | `path/to/file.ext:start-end` |

**Symptom.** <what the code does today, in 1-3 sentences. Quote the relevant line if helpful.>

**Why it matters.** <concrete consequence in *this* bot, in 1-3 sentences. "The model can't tell partial success from full success" beats "tool output should be clear".>

**Suggested fix.** <what to change, in 1-3 sentences. Be specific about the file and the shape of the change.>

**Verify.** <one or two ways to confirm the fix landed cleanly: a test name to add, a transcript event to look for, a metric to check, a manual reproduction.>

---

<repeat per finding>

## Architecture drift notes

<only include if Phase 2 found drift. List each item: what the architecture reference says, what's actually in the code now, recommended doc/code action. Skip the section entirely if there's no drift.>

## Suggested next steps

<3-5 bullets. The "what to do this week" digest. Each bullet = one finding ID + a one-line rationale, OR a small grouping of cheap wins. Order by what gets the most leverage per hour. The user should be able to read just this section and start working.>

---

*Generated by `tools/skills/mindcraft-code-review` on <ISO timestamp>. Diff this report against the previous one (`docs/code-review/`) to see what's new vs. previously known.*
````

## Findings JSON shape (intermediate, for subagents)

Subagents return findings as a JSON array. Each entry uses these exact keys:

```json
{
  "title": "Truncation in getBotOutputSummary deletes the most informative tail",
  "severity": "small-fix",
  "effort": "1-4h",
  "type": "design",
  "where": "src/agent/action_manager.js:178-204",
  "symptom": "The summarizer keeps the first ~500 and last ~100 chars of bot.output and drops the middle. For long mineflayer logs the actually-useful failure message lives at the tail of the kept-middle slice.",
  "why": "When mining fails, the model only sees pathfinder spam from the top of the log. It then issues another mineOre call instead of switching strategy.",
  "fix": "Replace the midpoint chop with a tail-biased keeper: drop the first 80% of the buffer past the cap and keep the trailing window. Add a one-line ERR_<code> prefix when the action ended in a recognizable error.",
  "verify": "Add a test in test/action_manager.test.js that constructs a synthetic 4kb log ending in 'no path found' and asserts the summary contains that string."
}
```

`id` is assigned by the merging step, not by subagents.

## Terminal summary template

ASCII only. Roughly 25 lines. Render to chat exactly:

```
Code review — <branch> (<mode>)
Files reviewed: <N> · Findings: <N> (major: <N>, small: <N>) · Hot-spots in scope: <N>

Top issues:
  1. [major-revision] <title>  →  <where>
  2. [major-revision] <title>  →  <where>
  3. [small-fix]      <title>  →  <where>
  4. [small-fix]      <title>  →  <where>
  5. [small-fix]      <title>  →  <where>

Full report: docs/code-review/<file>.md
Suggested next step: <one line lifted from "Suggested next steps" #1>
```

Show 3-5 top issues, fewer if total is small. If the report had a fallback path (couldn't write to `docs/code-review/`), put that as the first line of the summary.
