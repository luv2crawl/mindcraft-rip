## Project index (snapshot)

Mindcraft wraps a Mineflayer bot in a multi-LLM agent loop. Chat enters `Agent.handleMessage`, goes into `History`, is rendered by `Prompter`, and comes back as chat or a `!command(...)`; command output is appended as a system turn and can re-prompt the model. A 300ms update loop runs modes and self-prompting, while memory spans recent turns, a compact natural-language summary, structured world/session memory, and transcript logs.

- Prompter and models: `src/models/prompter.js`, `_model_map.js`, provider adapters, `src/utils/examples.js`.

### F-001 - SES lockdown wrapper recurses instead of locking down

| Field | Value |
| ----- | ----- |
| Severity | **major-revision** |
| Type | security |
| Effort | <30min |
| Where | `src/agent/library/lockdown.js:9-21` |

**Symptom.** The exported wrapper is named `lockdown` and calls `lockdown({...})` inside its own body. That name resolves to the wrapper itself, so the recursive call returns immediately after `lockeddown` is set and the SES global lockdown is never invoked.

**Why it matters.** `coder.js` calls this before evaluating generated `!newAction` code. The code still runs in a Compartment, but the intended process-wide SES hardening is silently skipped on the riskiest execution path in the bot.

**Suggested fix.** Call the SES global explicitly, such as `globalThis.lockdown({...})`, or rename the wrapper/import so the inner call cannot resolve to itself. Keep the idempotent guard, but only after the real SES lockdown succeeds.

**Verify.** Add a focused test around `src/agent/library/lockdown.js` that stubs or spies `globalThis.lockdown`, calls the wrapper twice, and verifies the SES call happens once with the expected options.

| Type | security |

| Where | `settings.js:42` |

### F-003 - Blocked commands mutate global command state across agents

| Field | Value |
| ----- | ----- |
| Severity | **major-revision** |
| Type | bug-risk |
| Effort | 1-4h |
| Where | `src/agent/commands/index.js:17-25` |

**Symptom.** `blacklistCommands` deletes entries from the module-level `commandMap`. That registry is shared by all Agent instances in a process, so one agent's blocked actions remove commands for other agents too.

**Why it matters.** Mindcraft supports multiple bots and task-specific blocked actions. A command blocked for one task can become `ERR_COMMAND_MISSING` for unrelated bots, producing wrong validation and misleading model feedback.

**Suggested fix.** Keep the global command registry immutable. Enforce per-agent policy in `commandExists`, `getCommandDocs`, and `executeCommand`, or give each Agent an isolated registry.

**Verify.** Add a multi-agent command test that blocks `!mineOre` for one fake agent and asserts another fake agent can still see and execute it.

### F-004 - MemoryBank accepts prototype-polluting memory keys

| Field | Value |
| ----- | ----- |
| Severity | **major-revision** |
| Type | security |
| Effort | 1-4h |
| Where | `src/agent/memory_bank.js:88-91,284-287` |

**Symptom.** `MemoryBank` writes caller-controlled namespace and record keys directly into plain objects. A name like `__proto__`, or loaded JSON with dangerous keys, can mutate prototypes instead of storing ordinary entries.

**Why it matters.** Structured memory keys can come from saved places, routes, storage labels, imports, and user-visible labels. In a long-running multi-bot process, prototype pollution can corrupt list/search/persistence behavior across namespaces.

**Suggested fix.** Reject or escape dangerous segments such as `__proto__`, `prototype`, and `constructor`, or store namespaces in null-prototype objects/Maps. Add a load-time migration guard that skips and logs unsafe keys from existing world files.

**Verify.** Add tests for `remember('places', '__proto__', ...)` and `loadJson({ places: { __proto__: ... } })` that assert `Object.prototype` is unchanged and inherited properties do not appear in `list` or `search`.

### F-006 - Chat events start overlapping handleMessage loops

| Field | Value |
| ----- | ----- |
| Severity | **major-revision** |
| Type | bug-risk |
| Effort | 1-2d |
| Where | `src/agent/agent.js:328-354` |

**Symptom.** The chat handler calls `this.handleMessage(username, translation)` without `await` or a `.catch()`. Rapid chat messages can start multiple model/command loops concurrently, and async failures bypass the local try/catch after the first await.

**Why it matters.** `handleMessage` mutates shared history, self-prompt state, last sender, bot output, and command execution state. Overlapping turns can answer stale context, interleave command results, and create unhandled rejections.

### F-007 - Structured world memory grows without retention or size limits

| Field | Value |
| ----- | ----- |
| Severity | **major-revision** |
| Type | perf |
| Effort | 1-2d |
| Where | `src/agent/memory_bank.js:8-17,88-91; src/agent/world_memory.js:223-238` |

**Symptom.** `MemoryBank` namespaces are unbounded objects, and `remember()` appends/replaces without quotas, eviction, or per-record size checks. `saveWorldMemory` clones and synchronously rewrites the full memory JSON on each save.

**Why it matters.** Routes, observations, storage facts, and imported world facts persist across sessions. As the file grows, prompt-summary ranking, search, clone, merge, and save work can stall the bot loop and inflate prompt-adjacent state.

**Verify.** Add a stress test that inserts thousands of observations and a long route, then asserts `getPromptSummary` and `saveWorldMemory` stay under expected time/size thresholds and prune deterministically.

### F-009 - Bot responder exact-match drops valid reasoning-model decisions

| Field | Value |
| ----- | ----- |
| Severity | small-fix |
| Type | correctness |
| Effort | <30min |
| Where | `src/models/prompter.js:555-561` |

**Symptom.** `promptShouldRespondToBot` returns true only when the raw trimmed lower-case model text is exactly `respond`. It does not strip reasoning artifacts or tolerate a short prefixed decision.

**Why it matters.** This classifier runs while another bot is talking during an active action. A reasoning model can return `</think>respond` or `Decision: respond`, which is treated as ignore, so the bot can miss stop/change requests from peers.

### F-010 - Gemini embeddings return wrapper objects instead of numeric vectors

| Field | Value |
| ----- | ----- |
| Severity | small-fix |
| Type | correctness |
| Effort | <30min |
| Where | `src/models/gemini.js:111-117; src/utils/examples.js:150-158` |

**Symptom.** `Gemini.embed` returns `result.embeddings` directly. The Google GenAI response shape stores numeric vectors under each embedding's `values` field, while example scoring passes the returned value into cosine similarity as `number[]`.

**Why it matters.** Gemini embedding profiles produce `NaN` similarity and fall back to word-overlap scoring for every comparison. That makes the configured embedding model ineffective for the examples that shape command style.

**Suggested fix.** Return `result.embeddings?.[0]?.values` and throw a clear error if it is missing or not an array of numbers.

**Verify.** Add a Gemini adapter test with a stubbed `{ embeddings: [{ values: [1, 0, 0] }] }` response and assert `embed()` returns `[1, 0, 0]`.

### F-017 - Force restart never escalates when the child ignores SIGINT

| Field | Value |
| ----- | ----- |
| Severity | small-fix |
| Type | bug-risk |
| Effort | 1-4h |
| Where | `src/process/agent_process.js:66-79` |

**Symptom.** `forceRestart()` sends SIGINT and sets a 5-second timer, but the timer only logs a warning. If the agent process is hung and does not exit, no replacement process is started and the old process remains running.

**Why it matters.** MindServer restart controls can leave an agent permanently stuck in the failure mode where an operator most needs restart to work. Server-side connection state can also remain ambiguous.

**Suggested fix.** After the grace period, escalate to a stronger kill and start a replacement only after the old process exits or is confirmed dead. Guard against double replacements if the process exits naturally during escalation.

**Verify.** Use a stub child process that ignores SIGINT, call `forceRestart()`, and assert the old child is terminated and a new child is spawned after the grace period.
