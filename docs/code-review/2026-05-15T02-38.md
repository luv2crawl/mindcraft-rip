## Project index (snapshot)

Mindcraft wraps a Mineflayer-based Minecraft bot in a multi-LLM agent loop. Player or system messages enter `Agent.handleMessage`, are stored in `History`, rendered through `Prompter` with current world state/examples/memory, and sent to a provider adapter. Model replies can contain chat or `!command(...)`; command output is appended back as system context and can trigger another prompt. Runtime state is split across recent history, a short natural-language memory summary, structured world/session memory, action/objective state, modes, self-prompting, multi-bot conversation routing, and transcript logging.

- Agent core: `src/agent/agent.js`, `history.js`, `action_manager.js`, `self_prompter.js`, `modes.js`.
- Prompter and models: `src/models/prompter.js`, `_model_map.js`, provider adapters, and example retrieval in `src/utils/examples.js`.
- Commands and objectives: `src/agent/commands/`, `src/agent/objectives/`, `src/agent/coder.js`, `src/agent/library/`.
- Memory: `MemoryBank`, world/session/storage/route memory, and world identity persistence.
- Vision: `src/agent/vision/` camera capture and vision prompting.
- Multi-bot and control plane: `conversation.js`, `connection_handler.js`, `mindserver_proxy.js`, `src/mindcraft/mindserver.js`, `main.js`, Python bridge files.
- Tests: `test/` covers agent loops, commands, memory, examples, objectives, transcripts, and helpers.

### F-001 - Self-prompter stop can miss the in-flight self prompt

| Field | Value |
| ----- | ----- |
| Severity | **major-revision** |
| Type | correctness |
| Effort | 1-4h |
| Where | `src/agent/self_prompter.js:130-158` |

**Symptom.** `stop()` and `pause()` set `this.interrupt` before calling `stopLoop()`, but `stopLoop()` returns immediately when `this.interrupt` is already true. `stop()` then sets state to `STOPPED`, and `shouldInterrupt()` only returns true for `ACTIVE` or `PAUSED`.

**Why it matters.** If `!endGoal` or another stop path fires while the self-prompt loop is inside `Agent.handleMessage`, the current self-prompt can continue. A stopped goal can still execute one more model-selected command because the interrupt predicate no longer fires.

**Suggested fix.** Separate "interrupt requested" from "stopLoop waiter already running", or make `stopLoop()` wait even when the flag was already set. Let `shouldInterrupt()` honor an interrupt flag for self prompts while a loop is active, regardless of the persisted state.

**Verify.** Add a self-prompter test where a loop is in an in-flight `handleMessage`, call `stop(false)`, return a command from the prompt, and assert command execution is not reached and `loop_active` clears.

### F-002 - Low-confidence world identities still get durable memory

| Field | Value |
| ----- | ----- |
| Severity | **major-revision** |
| Type | correctness |
| Effort | 1-4h |
| Where | `src/agent/world_memory.js:159-163; src/agent/world_identity.js:127-141` |

**Symptom.** Protocol and server fallback identities are marked `confidence: 'low'`, but `getWorldMemoryPath()` only blocks `confidence: 'temporary'`. A low-confidence protocol identity therefore gets a persistent `bots/_worlds/.../memory.json` file.

**Why it matters.** That identity is based on connection metadata, not the actual save identity. If a server host/port is reused for another world, places, storage, and routes can bleed into the wrong world.

**Suggested fix.** Do not return a durable memory path for low-confidence identities unless an explicit setting opts in. Store low-confidence memory in a session namespace and log why durable persistence was skipped.

**Verify.** Add a world-memory test where identity confidence is low and assert `getWorldMemoryPath()` returns null and no `_worlds` path is created.

### F-003 - Memory merge overwrites timestamp-less colliding records

| Field | Value |
| ----- | ----- |
| Severity | **major-revision** |
| Type | correctness |
| Effort | 1-4h |
| Where | `src/agent/world_memory.js:104-131` |

**Symptom.** `mergeMemoryJson()` treats place/storage/route-looking objects as whole records, then chooses incoming unless the existing timestamp is greater. If both timestamps are absent or unparsable, both compare as `0` and incoming always replaces the file record.

**Why it matters.** Legacy records and manually loaded memory can lack timestamps. A stale in-memory bank or a second bot saving the same world can silently erase newer file contents under the same key.

**Suggested fix.** Add an explicit equal-timestamp conflict policy: preserve existing, merge non-conflicting fields, or retain both records with conflict-suffixed keys. Ensure new writes include `updatedAt` and log collisions.

**Verify.** Add a world-memory test with an existing same-key record and incoming same-key record with no timestamps; assert the existing data is not silently overwritten.

### F-005 - Mode state is global across agents

| Field | Value |
| ----- | ----- |
| Severity | **major-revision** |
| Type | architecture-drift |
| Effort | 1-2d |
| Where | `src/agent/modes.js:443-549` |

**Symptom.** `modes_list`, `modes_map`, and `_agent` are module-level singletons. `initModes(agent)` overwrites `_agent`, while each bot receives a `ModeController` whose update and toggles operate on shared module state.

**Why it matters.** Mindcraft supports multiple agents. Initializing a second agent can make the first agent's `bot.modes.update()` operate on the second agent, and mode flags bleed between bots in one process.

**Suggested fix.** Move mode definitions and the current agent reference into a per-agent `ModeController`. Build fresh mode state in `initModes(agent)` and keep LLM-accessible APIs from exposing the agent reference.

**Verify.** Add a modes test that initializes two fake agents, toggles a mode on one, runs both updates, and asserts independent mode flags and agent references.

### F-006 - Generated code runs in-process with cooperative interruption only

| Field | Value |
| ----- | ----- |
| Severity | **major-revision** |
| Type | security |
| Effort | 1-2d |
| Where | `src/agent/coder.js:113-126; src/agent/coder.js:243-244; src/agent/library/lockdown.js:24-31` |

**Symptom.** Generated `main()` is awaited on the main Node event loop. The injected interrupt check is string-based and only appears after literal `;\n` sequences, so `while (true) {}` or another long synchronous loop can bypass interruption.

**Why it matters.** SES compartments restrict capabilities but do not meter CPU or preempt synchronous execution. One bad `!newAction` generation can hang the whole bot process, including timeouts, chat handling, and stop commands.

**Suggested fix.** Run generated code in a Worker thread or subprocess with a wall-clock kill path and a narrow message-based bot API. Keep cooperative `bot.interrupt_code` checks as a convenience, not as the isolation boundary.

**Verify.** Add an integration test that stages `while (true) {}` with a short timeout and asserts the bot process remains responsive and returns a timeout/interrupted result.

### F-007 - Persistent memory has no size or retention limits

| Field | Value |
| ----- | ----- |
| Severity | **major-revision** |
| Type | design |
| Effort | 1-2d |
| Where | `src/agent/memory_bank.js:118-123; src/agent/world_memory.js:223-238` |

**Symptom.** `MemoryBank.remember()` accepts arbitrary values into arbitrary namespaces with no per-record size limit, namespace cap, TTL, or eviction policy. `saveWorldMemory()` serializes the full memory bank on every save.

**Why it matters.** Long-running bots can accumulate unbounded observations, routes, and storage metadata. This slows every save, increases retrieval/prompt costs, and lets a single bad record bloat world memory indefinitely.

**Suggested fix.** Add namespace-specific limits: max records, max serialized record size, route breadcrumb caps, and pruning by timestamp. Record dropped/pruned counts in transcripts.

**Verify.** Add `MemoryBank` tests that insert oversized and excessive records per namespace and assert bounded saved JSON size.

### F-008 - handleMessage does not wait for history persistence before prompting

| Field | Value |
| ----- | ----- |
| Severity | small-fix |
| Type | correctness |
| Effort | <30min |
| Where | `src/agent/agent.js:535-544` |

**Symptom.** `handleMessage` adds the inbound message, calls `this.history.save()`, and immediately builds prompt history without awaiting the save. `History.save()` flushes pending summaries, while `History.add()` may have already spliced old turns out for async summarization.

**Why it matters.** When `max_messages` is reached, the next prompt can render while evicted turns are neither in short-term turns nor in long-term memory. The model can answer with missing recent context right when summarization is triggered.

**Suggested fix.** Await the pre-prompt `history.save()`, or split persistence from summary flushing and explicitly await `flushPendingSummary()` before `getHistory()`.

**Verify.** Add an `Agent.handleMessage` test with low `max_messages` and assert `promptConvo` receives either requeued turns or updated memory.

### F-009 - Conversation staleness guard can miss same-millisecond prompts

| Field | Value |
| ----- | ----- |
| Severity | small-fix |
| Type | bug-risk |
| Effort | <30min |
| Where | `src/models/prompter.js:353-361; src/models/prompter.js:414-421` |

**Symptom.** `promptConvo()` stamps prompts with `Date.now()` and compares timestamps to decide whether an older model response is stale.

**Why it matters.** Two prompt calls can start within the same millisecond during fast chat relay or batching. The older request can pass the stale checks and respond to superseded context.
