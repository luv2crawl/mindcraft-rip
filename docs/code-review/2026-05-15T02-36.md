## Project index (snapshot)

Mindcraft is a Mineflayer-based Minecraft bot wrapped in a multi-LLM agent loop: player (or system) messages enter `Agent`, land in `History`, are rendered by `Prompter` (templates, examples, world placeholders), and go to the configured chat model. The model replies with chat and/or `!command(...)`; `commands/index.js` parses and runs commands, and results return as system turns until `max_commands` or an empty model response. A 300ms `Agent.update` tick runs modes and `SelfPrompter`. Memory spans `History.turns`, the capped `History.memory` string, `MemoryBank`, and newer structured world/situational memory (`world_memory.js`, `session_memory.js`, `task_ledger.js`, etc.). `TranscriptLogger` records the run; `mindserver_proxy.js` ties optional multi-process UI orchestration.

### F-001 — Overlapping handleMessage runs without serialization

| Field | Value |
| ----- | ----- |
| Severity | **major-revision** |
| Type | bug-risk |
| Effort | 1-4h |
| Where | `src/agent/agent.js:355-362,442-544` |

**Symptom.** Inbound chat paths call `this.handleMessage(username, translation)` without `await`, and nothing globally serializes concurrent `handleMessage` invocations. Multiple events can enter the LLM/command loop at once.

**Why it matters.** `handleMessage` mutates shared `history`, `last_sender`, `bot.output`, objectives, and action state. Overlap produces out-of-order saves, confused command results, and difficult-to-reproduce “two brains” behavior under chat bursts, whispers, or system prompts.

**Suggested fix.** Add a per-agent message queue or a mutex around `handleMessage` (and any path that calls `promptConvo` / `executeCommand`), so only one reasoning loop runs unless an explicit preempt path is intended.

**Verify.** Integration-style test: delay `promptConvo`, fire two inbound messages, assert model/command calls and `history` mutations happen in a defined order.

### F-002 — History `save` and chunk eviction race the next prompt

| Field | Value |
| ----- | ----- |
| Severity | **major-revision** |
| Type | correctness |
| Effort | 1-4h |
| Where | `src/agent/agent.js:535-544`, `src/agent/history.js` (add/eviction paths) |

**Symptom.** After `history.add`, the code calls `this.history.save()` without `await` before entering the prompt loop. Eviction triggers async memory summarization; the next `getHistory()` can run after turns were removed but before `memory` reflects the summary.

**Why it matters.** The model can lose recently evicted context for that turn, producing contradictory plans (“forgot” user constraints) without a clear failure mode.

**Suggested fix.** `await` persistence when a summary or eviction is pending, or expose `await history.flushPendingWork()` before `getHistory()` / `promptConvo`.

**Verify.** Lower `max_messages`, stub slow `promptMemSaving`, cause eviction, assert the prompt either still sees removed turns or sees an updated `memory` string before the model call.

### F-003 — Command results can flood chat history and the next prompt

| Field | Value |
| ----- | ----- |
| Severity | **major-revision** |
| Type | cost |
| Effort | 1-4h |
| Where | `src/agent/commands/index.js:33,126-145,333-345`, `src/agent/agent.js:613-625` (downstream `history.add` of command output) |

**Symptom.** Transcript truncation caps logged command output, but the string returned to the agent and added to history is not uniformly capped before prompt construction. Unanchored `parseCommandMessage` also allows trailing junk to be treated as a valid parse for forced paths.

**Why it matters.** A single large query (for example wiki text) can dominate context, increasing cost and drowning useful state. Accepting trailing garbage weakens command validation semantics.

**Suggested fix.** Apply a single shared render cap (with explicit “truncated” metadata) before `routeResponse` / `history.add`. For parsing user/forced commands, use a full-string match or anchored parse while keeping the global extractor for model text.

**Verify.** Harness test: synthetic oversized command result; assert stored history and prompt stay under cap and include a truncation notice.

### F-006 — Concurrent `saveWorldMemory` can lose merged facts

| Type | bug-risk |
| Effort | 1-2d |
| Where | `src/agent/world_memory.js:219-238` |

**Symptom.** `saveWorldMemory` reads `memory.json`, merges, writes a pid-stamped temp file, then renames. Two processes saving the same world can both read the same baseline; last rename wins.

**Why it matters.** Multi-agent / multi-process setups silently drop one side’s new locations, routes, or storage notes.

### F-008 — `SelfPrompter.stop` / `stopLoop` interaction is fragile

| Field | Value |
| ----- | ----- |
| Severity | small-fix |
| Type | correctness |
| Effort | <30min |
| Where | `src/agent/self_prompter.js:130-147,157-165` |

**Symptom.** `stop()` sets `interrupt` then calls `stopLoop()` without `await`. `stopLoop` returns immediately if `interrupt` is already true, skipping the structured wait path. `handleUserPromptedCmd` also calls `stopLoop()` without `await`.

**Why it matters.** This has been a historical source of “stuck” or racy self-prompt behavior; ordering bugs are easy to introduce when expanding interrupts.

**Suggested fix.** Consolidate interrupt lifecycle: always `await stopLoop()` from `stop()`/`pause()`, and avoid double-setting `interrupt` before `stopLoop` can run its wait logic (or make `stopLoop` idempotent and always clear appropriately).

**Verify.** Tests for stop while inactive, stop during loop, and user-command interruption paths; assert `loop_active` and `interrupt` end in expected states.
