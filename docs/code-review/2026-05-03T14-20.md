## What changed in this rewrite

The original report mostly pointed at real issues, but several descriptions were hard to act on because they mixed symptoms, branch-summary expectations, and speculative failure modes. This version keeps the same finding set, but rewrites each finding around four concrete questions:

- What code is doing this?
- Why can that break the bot?
- What should change?
- How should the fix be verified?

Five findings were adjusted rather than copied as-is:

- F-001 is a source-of-truth/dirty-flag ownership issue, not proven data loss.
- F-011 is an API guardrail issue; the current mining caller already checks the frame id before popping.
- F-017 is real for object results with `ok: null` and no reason, but the original examples around void commands were inaccurate.
- F-027 is about missing global budget and ranking cost; the rendered structured memory is partially capped by namespace limits.
- F-030 is real for malformed or single-quoted command text; valid double-quoted args are less clear-cut than the original wording implied.

## Project index

This branch splits long-term memory into two layers:

- `History` still owns chat/session summary state in `bots/{bot_name}/memory.json`.
- `MemoryBank` now stores structured world facts by namespace: `places`, `journeymap.waypoints`, `routes`, `storage`, `observations`, and `pending`.
- `world_identity.js` resolves a world id.
- `world_memory.js` persists structured world memory to `bots/_worlds/{world_id}/memory.json`.
- `session_memory.js` holds runtime-only hints used by prompt memory retrieval.
- `Prompter.replaceStrings()` renders `$TEXT_MEMORY`, `$STRUCTURED_MEMORY`, and the legacy combined `$MEMORY`.

The main risk area is the transition from one bot-local `memory.json` file to a dual-file model. Several findings below are about keeping that migration predictable and preventing two memory sources from drifting.

## Findings

### F-001 - Dirty-flag ownership is unclear between bot memory and world memory

| Field | Value |
| ----- | ----- |
| Status | Adjusted |
| Severity | small-fix |
| Type | design |
| Effort | <30min |
| Where | `src/agent/history.js:177-192`, `src/agent/world_memory.js:68-87` |

**Problem.** `History.save()` writes `memory_bank` into the bot-local memory file, then calls `saveWorldMemory()`. If `saveWorldMemory()` returns false, `History.save()` marks the bank clean itself. If `saveWorldMemory()` succeeds, `saveWorldMemory()` marks it clean. That means two modules decide when structured world memory is clean.

**Impact.** The behavior is not obviously wrong today because the bot file still contains a copy of `memory_bank`, but it makes the persistence contract hard to reason about. This also conflicts with the stated architecture that world memory should be the durable owner of structured facts.

**Fix.** Pick one owner. Prefer moving `markClean()` into the structured-memory save path only, and treat bot-file `memory_bank` as legacy migration data rather than an active save target. If temporary world identity intentionally saves only to the bot file, encode that as an explicit fallback path.

**Verify.** Add tests for high-confidence, low-confidence, and temporary world identities. Each test should mutate `memory_bank`, call `history.save()`, and assert which file is written and when `isDirty()` flips to false.

### F-002 - Long action output keeps too little of the final error

| Field | Value |
| ----- | ----- |
| Status | Confirmed |
| Severity | major-revision |
| Type | correctness |
| Effort | <30min |
| Where | `src/agent/action_manager.js:187-201` |

**Problem.** `getBotOutputSummary()` splits long `bot.output` into the first 250 characters and last 250 characters. Long-running actions usually log progress first and the useful failure details last.

**Impact.** The model may receive a truncated final error instead of the reason it needs for the next prompt loop. That makes recovery commands less reliable.

**Fix.** Make truncation tail-biased. Keep a short prefix only for context, then spend most of the budget on the final output.

**Verify.** Add a test with a long output ending in a unique error string. Assert the summary contains the full sentinel.

### F-003 - Fast action-loop detection can still kill the whole agent

| Field | Value |
| ----- | ----- |
| Status | Confirmed |
| Severity | major-revision |
| Type | bug-risk |
| Effort | <30min |
| Where | `src/agent/action_manager.js:61-81` |

**Problem.** After more than five actions start within 20ms of the previous action, `_executeAction()` calls `agent.cleanKill()`.

**Impact.** Query-like or short internal commands can trip the same heuristic as a real movement loop. A false positive restarts the agent and loses in-memory context.

**Fix.** Replace the hard kill with `cancelResume()` plus an interrupt/transcript event. Apply the heuristic only to action labels that can actually create movement or digging loops.

**Verify.** Stub six rapid query-style actions and assert `cleanKill()` is not called. Repeat with a movement label and assert the resume is cancelled without killing the process.

### F-004 - Storage commands hide path failures and can leave containers open

| Field | Value |
| ----- | ----- |
| Status | Confirmed |
| Severity | major-revision |
| Type | bug-risk |
| Effort | <30min |
| Where | `src/agent/commands/actions.js:189-193`, `src/agent/commands/actions.js:795-824`, `src/agent/commands/actions.js:908-953` |

**Problem.** `openStorageAt()` ignores the boolean returned by `goToPositionChunked()`. `!indexStorage` and `!restockFromStorage` then continue as if navigation succeeded. Both commands also close containers only on the success path.

**Impact.** A pathfinding failure can be reported as `storage_block_missing`, which sends the model toward the wrong recovery. If container operations throw, the container may remain open.

**Fix.** Return a structured navigation result from `openStorageAt()`. Surface `no_path` when pathfinding fails. Wrap container operations in `try/finally` and close with a best-effort catch.

**Verify.** Mock pathfinding to return false and assert the command returns `no_path`. Mock `withdraw()` or `containerItems()` to throw and assert `close()` still runs.

### F-005 - Memory keys are case-sensitive at write and exact lookup

| Field | Value |
| ----- | ----- |
| Status | Confirmed |
| Severity | major-revision |
| Type | correctness |
| Effort | <30min |
| Where | `src/agent/memory_bank.js:58-85`, `src/agent/commands/actions.js:764-824` |

**Problem.** `MemoryBank.remember()` stores the key exactly as provided, and `recall()` looks up that exact key. `Base`, `base`, and `BASE` become different records.

**Impact.** User and model casing differences can fork places, waypoints, and storage labels. Commands like `!labelNearestStorage("Base")` followed by `!indexStorage("base")` will not find the saved record.

**Fix.** Normalize keys at the memory boundary. Lowercase or otherwise canonicalize keys in `remember()`, `recall()`, and `search()`. During `loadJson()`, collapse duplicate keys with a deterministic winner, preferably latest `verifiedAt` or `updatedAt`.

**Verify.** Store `Base`, recall `base` and `BASE`, and assert all return the same record. Add the same coverage for storage labels.

### F-006 - JourneyMap bridge fetches have no timeout

| Field | Value |
| ----- | ----- |
| Status | Confirmed |
| Severity | major-revision |
| Type | bug-risk |
| Effort | <30min |
| Where | `src/agent/journeymap.js:53-66`, `src/agent/agent.js:224-254` |

**Problem.** `bridgeFetch()` calls `fetch()` without an `AbortController`. Startup sync awaits this path from `_syncJourneyMapOnStart()`.

**Impact.** A bridge that accepts a connection but never responds can hang `!syncJourneyMap`, `!exportWaypoint`, or startup sync. During startup, chat handlers are not installed until after world memory and JourneyMap sync complete.

### F-007 - World-memory load can treat wrapper JSON as legacy places

| Field | Value |
| ----- | ----- |
| Status | Confirmed |
| Severity | major-revision |
| Type | bug-risk |
| Effort | <30min |
| Where | `src/agent/world_memory.js:23-27`, `src/agent/memory_bank.js:247-265` |

**Problem.** `loadWorldMemory()` passes `data.memory_bank || data` into `MemoryBank.loadJson()`. If the world file is valid JSON but missing `memory_bank`, `MemoryBank` treats the wrapper object as legacy flat place data.

**Impact.** Keys like `world_identity` or `saved_at` can become fake place records. Because parsing succeeds, the corrupt-backup path never runs.

**Verify.** Write `{ "world_identity": {}, "saved_at": "..." }` as a world file. Loading should produce an empty bank plus a `world_memory.load.failure` event, not fake places.

### F-008 - Structured memory is still saved in both memory files

| Field | Value |
| ----- | ----- |
| Status | Confirmed |
| Severity | major-revision |
| Type | architecture-drift |
| Effort | 1-4h |
| Where | `src/agent/history.js:177-192`, `src/agent/history.js:223-234` |

**Problem.** `History.save()` writes `memory_bank` into `bots/{bot_name}/memory.json`, while `world_memory.js` writes the same bank into `bots/_worlds/{world_id}/memory.json`.

**Impact.** There are two sources of truth. Load order currently means bot memory can be loaded first and then replaced by world memory. This makes migration behavior harder to reason about and keeps re-emitting legacy data forever.

**Fix.** Stop writing `memory_bank` into the bot-local file after migration. Keep bot-file `memory_bank` only as legacy input when the world file does not exist or when explicitly merging legacy entries.

**Verify.** After saving with a high-confidence world id, assert `bots/{bot_name}/memory.json` has no `memory_bank` field and the world file does.

### F-009 - Structured-memory namespaces have no eviction policy

| Field | Value |
| ----- | ----- |
| Status | Confirmed |
| Severity | major-revision |
| Type | design |
| Effort | 1-4h |
| Where | `src/agent/memory_bank.js:73-78`, `src/agent/commands/actions.js:73-128`, `src/agent/journeymap.js:123-153` |

**Problem.** Observations use timestamped keys, JourneyMap imports merge into an unbounded waypoint namespace, route breadcrumbs can grow for long recordings, and `pending` writes tombstones such as `route_recording: null`.

**Impact.** The prompt view is capped, but the on-disk file and ranking work are not. Long-running worlds will accumulate memory indefinitely unless users manually prune it.

**Fix.** Add per-namespace limits and cleanup rules. Examples: cap observations by `createdAt`, remove pending entries when value is null, cap or compact routes, and optionally cap bridge-imported waypoints.

**Verify.** Insert more records than the cap and assert only the newest or highest-priority entries remain after `remember()` and `loadJson()`.

### F-010 - The prompt says one command, but the loop executes batches

| Field | Value |
| ----- | ----- |
| Status | Confirmed |
| Severity | major-revision |
| Type | correctness |
| Effort | 1-4h |
| Where | `src/agent/agent.js:503-585`, `profiles/defaults/_default.json` |

**Problem.** The default profile says to use at most one command per response and wait for results. `handleMessage()` now extracts every command from the model response and executes the full batch before re-prompting.

**Impact.** The second command in a batch cannot react to the first command's result. If command one fails or changes context, command two still runs.

**Fix.** Decide the contract. If the one-command rule is intended, execute only the first command and log dropped extras. If command batching is intended, update the profile and examples so the model knows commands run without intermediate reasoning.

**Verify.** Add a stub LLM response containing two commands. Assert the behavior matches the chosen contract.

### F-011 - ObjectiveStack.pop() has no built-in identity check

| Field | Value |
| ----- | ----- |
| Status | Adjusted |
| Severity | small-fix |
| Type | design |
| Effort | 1-4h |
| Where | `src/agent/objectives/objective_stack.js:29-41`, `src/agent/objectives/mining_objective.js:90-93` |

**Problem.** `ObjectiveStack.pop()` always pops the top frame. The current mining objective checks `peek()?.id === frame.id` before calling it, but the stack API itself does not enforce that guard.

**Impact.** Future callers can accidentally pop a sibling or parent frame and record the wrong objective as completed or failed.

**Fix.** Add optional `expectedId` or `expectedType` parameters to `pop()`. On mismatch, record `objective.pop.mismatch` and leave the stack unchanged.

**Verify.** Push frames A and B. Call `pop({ expectedId: A.id })` while B is on top and assert B remains on the stack.

### F-012 - Multiple bots can overwrite the same world-memory file

| Field | Value |
| ----- | ----- |
| Status | Confirmed |
| Severity | major-revision |
| Type | bug-risk |
| Effort | 1-4h |
| Where | `src/agent/world_memory.js:68-87` |

**Problem.** Every bot with the same world id writes the same `bots/_worlds/{world_id}/memory.json` file from its local in-memory bank. There is no lock or read-merge before rename.

**Impact.** Bot A can save place A, bot B can save place B, and the last writer wins. The first bot's new memory disappears.

**Verify.** Simulate two agents loading the same world file, saving distinct places, and reloading. Both places should survive.

### F-017 - Object results with unknown ok state can become ERR_EXCEPTION

### F-030 - Command extraction can treat malformed inner text as commands

| Field | Value |
| ----- | ----- |
| Status | Adjusted |
| Severity | small-fix |
| Type | bug-risk |
| Effort | 1-4h |
| Where | `src/agent/commands/index.js:29-58` |

**Problem.** `extractCommandMessages()` scans with a global regex. When a command is malformed or uses unsupported quoting, the outer command may be matched without its argument list, and later `!name` text can be extracted as another top-level command.

**Impact.** Descriptive text inside a malformed command can become executable command text. This is more likely now that the message loop executes every extracted command.

**Fix.** Track match spans and ignore matches that fall inside a previous command span. Also consider anchoring commands to line starts or whitespace boundaries and supporting only one quoting mode consistently.

**Verify.** Add tests for valid double-quoted command args, unsupported single-quoted args, and malformed nested command text. The extractor should never execute descriptive inner text as a second command.

### F-031 - Summary backpressure can let turns exceed max_messages

| Field | Value |
| ----- | ----- |
| Status | Confirmed |
| Severity | small-fix |
| Type | design |
| Effort | 1-4h |
| Where | `src/agent/history.js:138-174` |

**Problem.** While `summary_in_progress` is true, new turns are appended but eviction is skipped. When summarization finishes, the next add evicts only one chunk.

**Impact.** Under sustained chat or slow summarization, `turns` can stay well above `max_messages`, increasing prompt size.

**Fix.** After a summary finishes, drain backpressure in a loop until `turns.length < max_messages`, or schedule another summary immediately. Record a transcript event when the buffer grows beyond a threshold.

**Verify.** Hold `promptMemSaving()` pending, add many turns, release it, and assert the buffer returns below the limit within bounded follow-up work.
