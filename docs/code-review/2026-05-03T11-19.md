## Project index (snapshot)

## Findings

### F-001 - Prompt memory selection is relevance-blind after eight labels

| Field | Value |
| ----- | ----- |
| Severity | **major-revision** |
| Type | design |
| Effort | 1-2d |
| Where | `src/agent/memory_bank.js:120-138` |

**Symptom.** `getPromptSummary()` sorts each namespace alphabetically and includes only the first eight records. It does not use the current user message, active objective, current location, command intent, or recent records to choose relevant places, waypoints, routes, or storage labels.

**Why it matters.** Once a bot has more than eight saved waypoints or storage labels, a relevant record such as `MAIN_BASE`, `home_chest`, or a named storage container can be persisted but omitted from the prompt. The model then behaves as if the memory does not exist unless it guesses the right query command.

**Suggested fix.** Add a deterministic memory-context builder before adding any extra model loop. Pass the latest user/system intent and active objective into `MemoryBank.getPromptSummary(context)`, rank exact key/value matches and critical aliases (`home_chest`, `MAIN_BASE`, `base`, active route, current objective resources) ahead of alphabetical fallback, and only then cap output. Consider an optional cheap planning/context-gathering prompt later for ambiguous requests, not as the first fix.

**Verify.** Add a `test/prompter.test.js` or `test/situational_memory.test.js` case with more than eight waypoints where the requested waypoint sorts after the cutoff, then assert the rendered prompt includes that waypoint.

### F-002 - Structured memory is fed back into the text-memory summarizer

| Field | Value |
| ----- | ----- |
| Severity | **major-revision** |
| Type | correctness |
| Effort | 1-4h |
| Where | `src/models/prompter.js:176-183,390-393` |

**Symptom.** `$MEMORY` now expands to both `History.memory` and `MemoryBank.getPromptSummary()`. `promptMemSaving()` renders the `saving_memory` profile through the same replacement path, so the summarizer sees structured memory as part of "Old Memory".

**Why it matters.** The summary model can copy, rewrite, truncate, or duplicate structured facts into the 500-character text memory, creating two inconsistent versions of the same durable state. This also wastes the already tight summary budget and makes later prompts harder to reason about.

**Suggested fix.** Split prompt placeholders into `$TEXT_MEMORY` and `$STRUCTURED_MEMORY`, or add an option to `replaceStrings` such as `{ includeStructuredMemory: false }` for `promptMemSaving()`. Keep structured facts authoritative in `MemoryBank`; the natural-language summary should reference only conversational/user preferences unless explicitly promoted.

**Verify.** Add a prompter test that renders `saving_memory` with a seeded `MAIN_BASE` waypoint and asserts the old-memory block contains only `History.memory`, while conversation prompts still include structured memory.

### F-003 - Save can persist neither evicted turns nor their summary

| Field | Value |
| ----- | ----- |
| Severity | **major-revision** |
| Type | correctness |
| Effort | 1-4h |
| Where | `src/agent/history.js:147-171; src/agent/agent.js:389-390; src/agent/agent.js:483` |

**Symptom.** `History.add()` splices a chunk out of `turns`, starts `pending_summary` asynchronously, and returns before that chunk is reflected in `History.memory`. `Agent.handleMessage()` can call `history.save()` immediately after the add or after the command loop.

**Why it matters.** A restart after that save but before the summary finishes can produce `memory.json` with the chunk removed from `turns` and not yet included in `memory`. Durable instructions discussed in chat, including "use MAIN_BASE as a backup", can disappear from the only state loaded next session.

**Suggested fix.** Make `History.save()` flush pending summaries before writing, or persist pending summary chunks alongside `turns` until summarization commits. A practical approach is `History.flushPendingSummary()` plus a crash-safe `pending_summary_chunks` field in `memory.json`.

**Verify.** Add a history test with delayed `promptMemSaving`, trigger eviction, call `save()` before `pending_summary` resolves, reload, and assert the evicted durable turn is still recoverable.

### F-004 - Action wrapper hides mining objective failure codes behind OK output

| Field | Value |
| ----- | ----- |
| Severity | **major-revision** |
| Type | correctness |
| Effort | 1-4h |
| Where | `src/agent/commands/actions.js:39-45,713-715` |

**Symptom.** `runAsAction()` discards the return value from the wrapped action and returns the `ActionManager` bot-output summary. `!mineOre` awaits `runMiningObjective()` but does not return its formatted objective result directly.

**Why it matters.** Mining failures such as `missing_home_chest`, `missing_supplies`, or `unsafe_mining_start` are model-steering results. When they are buried under an action-output wrapper, `normalizeCommandResult()` can classify the command as OK, so the next model turn may not recover by querying or setting memory.

**Suggested fix.** Have `runAsAction()` capture and prefer an explicit wrapped return value when one exists. Make `!mineOre` return `await runMiningObjective(agent, ore_name, num)`; keep bot-output summaries only as a fallback for legacy actions that only log.

**Verify.** Add a command test with a stub action returning `FAILED: missing_home_chest` through `runAsAction` and assert `renderCommandResult()` starts with `ERR_MISSING_HOME_CHEST`, not `OK`.

### F-005 - memory.json writes are not atomic and corrupt files abort load

| Field | Value |
| ----- | ----- |
| Severity | **major-revision** |
| Type | bug-risk |
| Effort | 1-4h |
| Where | `src/agent/history.js:175-229` |

**Symptom.** `History.save()` writes directly to `bots/{name}/memory.json` with `writeFileSync`. `History.load()` parses that file directly and throws on invalid JSON.

**Why it matters.** An interrupted write can corrupt the one file that contains chat memory, self-prompt state, and typed map/storage memory. On the next start, the bot can fail to load instead of recovering, which is exactly the scenario that makes users relabel waypoints and storage.

**Suggested fix.** Write to a sibling temporary file, then rename it over `memory.json`. On load failure, move the corrupt file to a timestamped backup, initialize a clean memory state, and record a transcript warning.

**Verify.** Add a `test/history.test.js` case that creates invalid JSON at `memory.json`, calls `History.load()`, and asserts the agent starts with empty memory while preserving a backup file.

### F-006 - Unknown typed memory namespaces are discarded on reload

| Field | Value |
| ----- | ----- |
| Severity | **major-revision** |
| Type | architecture-drift |
| Effort | 1-4h |
| Where | `src/agent/memory_bank.js:33-41,157-175` |

**Symptom.** `MemoryBank.remember()` can create arbitrary nested namespaces from a dotted type, but `loadJson()` only copies the fixed namespaces from `_emptyMemory()`. Future namespaces such as `farms`, `portals`, or `biomes` can survive `getJson()` and then silently disappear on reload.

**Why it matters.** The live code is evolving toward a typed memory layer, but persistence is still partly fixed-schema. New durable facts may appear to save correctly during a session and vanish across sessions.

**Suggested fix.** Choose one contract: enforce a fixed namespace registry in `remember()`, or preserve unknown plain-object namespaces during `loadJson()`. If extensibility is intended, merge defaults with all plain-object keys from the saved JSON, then repair known namespaces such as `journeymap.waypoints`.

**Verify.** Add a test that saves `remember('portals.nether_hub', 'home', record)`, reloads into a new `MemoryBank`, and asserts the portal record still exists.

### F-007 - JourneyMap waypoints are not reconciled automatically on startup

| Field | Value |
| ----- | ----- |
| Severity | **major-revision** |
| Type | design |
| Effort | 1-4h |
| Where | `src/agent/agent.js:90-94; src/agent/commands/actions.js:301-314` |

**Symptom.** Startup only loads `memory.json`. JourneyMap bridge import happens only when the model or user runs `!syncJourneyMap`.

**Why it matters.** If `memory.json` is empty, stale, or was reset, existing JourneyMap waypoints in the same world remain invisible until an explicit sync command. From the user's perspective, the bot has "forgotten" map labels and needs relabeling even though the external map source still has them.

**Suggested fix.** Add an opt-in setting such as `auto_sync_journeymap_on_start`. After the bot is initialized and memory is loaded, attempt a non-fatal bridge sync, merge changed waypoints into `memory_bank`, and save if dirty. Do not block startup if the bridge is unavailable.

**Verify.** Add a startup/integration test with a mocked bridge returning `MAIN_BASE`; start with an empty memory bank and assert the waypoint is imported and saved without a user command.

### F-008 - setHomeChest saves a chest as a place, not storage

| Field | Value |
| ----- | ----- |
| Severity | small-fix |
| Type | correctness |
| Effort | 1-4h |
| Where | `src/agent/commands/actions.js:718-742` |

**Symptom.** `!setHomeChest` stores `home_chest` with `memory_bank.rememberPlace()` only. The storage namespace is not updated, no block type is recorded, and storage commands such as `!indexStorage("home_chest")` look only in storage memory.

**Why it matters.** The bot can successfully save a mining chest and still behave as if no named storage exists for storage indexing/search. That splits "home chest" and "storage" memory in a way users will read as forgetfulness.

**Suggested fix.** When a chest is found, also persist a storage record named `home_chest` using `makeStorageRecord()` with block metadata and dimension. Keep the place alias for backward compatibility.

**Verify.** Add a command test for `!setHomeChest` with a fake nearby chest and assert both `recall('places', 'home_chest')` and `recall('storage', 'home_chest')` exist.

### F-009 - Area indexing creates duplicate generic storage labels

| Field | Value |
| ----- | ----- |
| Severity | small-fix |
| Type | design |
| Effort | 1-4h |
| Where | `src/agent/commands/actions.js:829-844` |

**Symptom.** `!indexStorageArea` writes each scanned container under `storage_${x,y,z}`. It does not check whether the same position key is already saved under a user label such as `home_chest` or `ore_chest`.

**Why it matters.** A user can label storage once, scan the base later, and then see `!findInStorage` report generic `storage_...` names instead of the remembered labels. That looks like label loss even though the coordinate matches.

**Suggested fix.** Before writing a scanned container, search existing storage records for the same `key` and dimension. Refresh the existing user-labeled record or store aliases so search results prefer labels over generated names.

**Verify.** Seed `storage.home_chest`, run the area-indexing path over the same block, and assert refreshed counts remain under `home_chest` with no duplicate generated result.

### F-010 - Numeric dimension 0 is treated as missing in storage/export paths

| Field | Value |
| ----- | ----- |
| Severity | small-fix |
| Type | correctness |
| Effort | <30min |
| Where | `src/agent/storage_memory.js:23; src/agent/commands/actions.js:391,757-759,916-918` |

**Symptom.** Several memory/export paths use `value || null` for dimensions. A valid numeric dimension `0` is therefore stored or exported as null or replaced by the current bot dimension.

**Why it matters.** Imported map locations and storage facts can silently lose dimension identity. That weakens cross-session navigation and base/chest selection when saved facts span dimensions.

**Suggested fix.** Use nullish coalescing for dimension fields: `extra.dimension ?? null` and `marker.dimension ?? agent.bot.game?.dimension ?? null`. Audit storage, route, and export helpers for the same falsy-dimension pattern.

**Verify.** Add tests that create a storage record with `dimension: 0` and export a marker with `dimension: 0`; assert both outputs preserve numeric zero.

## Architecture drift notes

- The skill architecture reference still describes `src/agent/memory_bank.js` as a flat key-value store. The live code has typed namespaces (`places`, `journeymap.waypoints`, `routes`, `storage`, `observations`, `pending`) and prompt summarization. Update the reference so future changes do not reintroduce flat-memory assumptions.
- The architecture reference says a response containing a command is truncated to the first command. The live `Agent.handleMessage()` now extracts and executes multiple commands serially. This matters for memory mutation ordering and save expectations.
