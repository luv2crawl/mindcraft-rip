### F-001 - `!planMiningRun` reports ready without preflighting descent terrain

| Field | Value |
| ----- | ----- |
| Severity | **major-revision** |
| Type | correctness |
| Effort | 1-4h |
| Where | `src/agent/library/skills.js:2932-2965` |

**Symptom.** `planMiningRun` validates ore name, deposit chest, and inventory supplies, then returns `ready` without checking whether the current position can start a descent. In the current session it reported `Ready to mine 32 Coal` while the bot was standing at a base-edge/shaft position where `digStaircaseTo` aborted at Y=70 before taking a step.

**Why it matters.** The model treats `!planMiningRun` as a green light. If "ready" only means inventory-ready, the next `!mineOre` can fail immediately on terrain and the model has no precondition it can satisfy.

**Suggested fix.** Add a terrain preflight to `planMiningRun`: compute target Y, call the same descent-start selector used by `digStaircaseTo`, and include a `missing.safe_mining_start` or `reason: unsafe_mining_start` when no valid start exists. If a nearby valid start exists, include it in `plan.data.miningStart` so `!mineOre` can use the same decision.

**Verify.** Add a `planMiningRun reports unsafe_mining_start beside shaft` test that models the screenshot: current block near open air, no safe adjacent descent, and no nearby start. The plan should not return `ok: true`.

### F-002 - `!mineOre` uses the chat position as the mining entry

| Field | Value |
| ----- | ----- |
| Severity | **major-revision** |
| Type | design |
| Effort | 1-4h |
| Where | `src/agent/library/skills.js:3575-3617` |

**Symptom.** `mineOreAt` snapshots `requestedEntry` from the bot's current position, prepares supplies at the chest, returns to that exact position, saves it as `mining_entry`, and starts the descent there. When the user gives the command from the base or next to the home chest, the bot tries to mine from the base wall/shaft edge.

**Why it matters.** "Home chest location" and "safe mine entrance" are different preconditions. Mining from the base entrance can hit glass, open shafts, storage blocks, protected build blocks, or water exposure before actual mining begins.

**Suggested fix.** Introduce a separate `selectMiningEntry(bot, oreName, chestPos, options)` step before descent. It should prefer an explicitly remembered `mining_entry` when valid, otherwise choose a nearby natural/solid start away from storage and open shafts. Save that chosen entry, and only return to the original user position if it was selected as safe.

**Verify.** Add an integration-style unit test for `mineOreAt` setup using a fake bot at `(118,70,-116)` beside a shaft and chest; assert it chooses a separate `mining_entry` instead of saving the starting block.

### F-003 - Staircase direction changes are discarded before branch mining

| Field | Value |
| ----- | ----- |
| Severity | **major-revision** |
| Type | correctness |
| Effort | 1-4h |
| Where | `src/agent/library/skills.js:3468-3501`, `src/agent/library/skills.js:3642-3700` |

**Symptom.** `digStaircaseTo` can choose a different direction from the requested one, and it can turn mid-descent when the current direction becomes unsafe. It returns only a boolean. After descent, `mineOreAt` still logs and branch-mines using the original `direction` from `options.direction || 'south'`.

**Why it matters.** If the descent avoided the first bad direction, the branch phase can immediately resume mining toward the same unsafe side. It also makes logs misleading: the bot may descend east but then report and mine south.

**Suggested fix.** Have `digStaircaseTo` return an object such as `{ ok, direction, stepsTaken, start, end, failure }`. `mineOreAt` should use the returned final direction for branch mining and torch placement.

**Verify.** Add a test where preferred south is unsafe but east is safe; assert `mineOreAt` branch-mines with east after successful descent.

### F-004 - Descent failure loses the actionable reason

| Field | Value |
| ----- | ----- |
| Severity | small-fix |
| Type | bug-risk |
| Effort | <30min |
| Where | `src/agent/library/skills.js:3501-3504`, `src/agent/library/skills.js:3617-3627` |

**Symptom.** Staircase failure collapses to `false`, then `mineOreAt` returns `reason: 'descent_failed'` with only `targetY` and `currentY`. The useful reason, such as `floor:air`, `fluid:water`, `blocked:bedrock`, or `path_to_start_failed`, is not preserved in the structured result.

**Why it matters.** The model sees "descent_failed" and repeats mining or asks if it is stuck. It cannot tell whether the next action should be "move away from base edge", "bridge floor", "choose a new entry", or "avoid water".

**Suggested fix.** Return structured failure details from `_staircaseStepDown`, `_moveToNearbyStaircaseStart`, and `digStaircaseTo`. Bubble them into `mineOreAt` as `data.failure`, `data.failureBlock`, `data.failurePosition`, and `data.recommendedCommands`.

**Verify.** Add a test with an air floor under the first step and assert the final mining result includes `data.failure === 'floor:air'` or equivalent.

### F-005 - Action output truncation can hide the descent diagnostic

| Field | Value |
| ----- | ----- |
| Severity | small-fix |
| Type | design |
| Effort | 1-4h |
| Where | `src/agent/action_manager.js:187-195` |

**Symptom.** `getBotOutputSummary` keeps the first 250 and last 250 chars of long output. Mining produces setup logs, pathfinder logs, and final objective logs; the specific staircase reason can land in the discarded middle.

**Why it matters.** The command output is the model's recovery signal. If the reason line is omitted, the next prompt sees only a generic failure and is likely to retry the same command.

**Suggested fix.** Add a structured error tail to action results, or make mining log a final one-line summary such as `FAILED_DESCENT: floor air at x,y,z; suggested move-to-start x,y,z`. Alternatively, tail-bias the summary for failed actions.

**Verify.** Add an `action_manager` test with synthetic mining output where the key failure line is in the middle and assert the summary still contains the final structured error line.

### F-006 - Mining examples encourage plan-only responses for direct mining tasks

| Field | Value |
| ----- | ----- |
| Severity | small-fix |
| Type | design |
| Effort | <30min |
| Where | `profiles/defaults/_default.json:70-85` |

**Symptom.** The most direct mining examples answer "mine some iron ore" with `!planMiningRun(...)`; only the multi-turn "do it" example proceeds to `!mineOre(...)`. In the current session, "mine 32 units of coal" produced only `!planMiningRun("coal", 32)`, and the user had to ask "are you stuck?" before the bot saved the chest and later ran `!mineOre`.

**Why it matters.** For user commands phrased as an imperative mining task, a plan-only response looks like inaction. The model should plan when asked to plan, but it should either execute after a ready plan or use `!mineOre` directly when the command already includes the target and count.

**Suggested fix.** Update the default examples so one single-turn mining imperative uses `!mineOre(...)`, and keep `!planMiningRun(...)` for "can I mine" or "plan a mining run" wording. Add an example where the plan result is ready and the next assistant action is `!mineOre`.

**Verify.** Update `test/examples.test.js` so "mine 32 units of coal" or "mine some iron ore" retrieves at least one executable `!mineOre(...)` example, not only plan-only examples.
