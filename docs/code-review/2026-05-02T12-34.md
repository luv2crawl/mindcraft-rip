## Project index (snapshot)

Mindcraft wraps a Mineflayer-based Minecraft bot in a multi-LLM agent loop. A player chat enters `Agent`, gets added to `History`, is rendered into a prompt by `Prompter` (template + retrieved examples + current world state), and is sent to the configured chat model. The model responds with chat or a `!command(...)`. Commands run via the dispatcher in `commands/index.js`, their output is appended back to `History` as a system turn, and the model is prompted again — this is the reasoning loop. A 300ms tick updates `modes` and the `SelfPrompter`. Memory has three layers: recent turns in `History.turns`, a long-term running summary in `History.memory` (500-char hard cap), and structured facts in `MemoryBank`. Everything is observed via `TranscriptLogger`.

Subsystems and primary files (post-branch state):

- **Agent core**: `src/agent/agent.js`, `history.js`, `action_manager.js`, `self_prompter.js`, `modes.js`, `memory_bank.js`, `transcript_logger.js`.
- **Commands & objectives**: `src/agent/commands/{index,actions,queries}.js`, `src/agent/coder.js`, `src/agent/objectives/{objective_stack,objective_results,mining_objective}.js` *(new this branch)*.
- **Library / skills**: `src/agent/library/skills.js` (3,519 lines), `skill_library.js`, `lockdown.js`, `full_state.js`, `world.js`, `ore_data.js` *(new)*, `minecraft_ores.json` *(new)*.
- **Prompter & models**: `src/models/prompter.js`, `_model_map.js`, `{gpt,claude,gemini,…}.js` provider adapters.
- **Retrieval / utils**: `src/utils/{examples,text,mcdata,keys,math,translator}.js`.
- **Tools (developer-only)**: `tools/explorer/` (the local dashboard, also added on this branch).

### F-001 — ObjectiveStack frames are never popped on failure paths in mining_objective

| Field | Value |
| ----- | ----- |
| Severity | **major-revision** |
| Type | bug-risk |
| Effort | 1-4h |
| Where | `src/agent/objectives/mining_objective.js:30-72` |

**Symptom.** `runMiningObjective` only calls `agent.objectives.pop` on the `ok==true` branch (line 61). The plan-failure early return (lines 30–34), the partial / non-ok finish (lines 55–59), and the catch block (lines 65–72) all `updateTop` to `'failed'` but leave the frame on the stack.

**Why it matters.** After any failed mining run — including the FAILED:partial case the structured-result rework was *introduced to fix* — the stack accumulates dead frames. The next `!objectives` query (and `getSummary` in any system context) shows stale failed frames forever, growing context cost, confusing the LLM's planning, and breaking the invariant that `peek()` returns the active goal.

**Suggested fix.** Always pop the frame in a `finally` block (or in every terminal branch) after writing the final result. Decide whether failed frames should pop with a failed result (current `pop()` already supports it via `frame.result.ok===false`) or be archived elsewhere; pick one and apply consistently.

**Verify.** Add a unit test `mining_objective_failure_pops_frame`: stub `planMiningRun` to return `{ok:false, reason:'unknown_ore'}`, call `runMiningObjective`, assert `agent.objectives.frames.length === 0`. Repeat for the partial-mined and exception paths.

### F-002 — `lockdown()` invoked inside `generateCode` instead of at module load

| Field | Value |
| ----- | ----- |
| Severity | **major-revision** |
| Type | security |
| Effort | 1-4h |
| Where | `src/agent/coder.js:33` |

**Symptom.** `lockdown()` is called the first time `generateCode` runs, after the agent, mineflayer, conversation manager, settings, etc. have already initialized and freely mutated `globalThis`. Subsequent calls short-circuit via the `lockeddown` flag.

**Why it matters.** SES lockdown freezes the global object at the moment it runs. Anything an attacker (or a buggy plugin) put on `globalThis` before that first `!newAction` is preserved untouched into every Compartment; conversely, late lockdown can break things that were configuring globals on the assumption they're mutable. `!newAction` is the explicit untrusted-LLM-code surface — it deserves a deterministic, single boot-time lockdown.

**Suggested fix.** Call `lockdown()` once from the agent bootstrap (e.g. at the top of `agent.js` or a dedicated init module imported first), before any third-party module touches `globalThis`. Remove the per-call invocation in `coder.js`. Keep an idempotent guard for safety.

**Verify.** Emit `ses.lockdown.applied` exactly once at startup; assert in an integration test that it fires before the first `agent.bot` connect and that a second `!newAction` does not emit it again.

### F-003 — Memory chunks lost when `summarizeMemories` times out or fails

| Field | Value |
| ----- | ----- |
| Severity | **major-revision** |
| Type | correctness |
| Effort | 1-4h |
| Where | `src/agent/history.js:34-64,93-117` |

**Symptom.** `add()` splices the chunk out of `turns` and queues a non-blocking `summarizeMemories`. If the call times out (default 20s) or throws, the catch returns early without updating `this.memory` or restoring the chunk. The chunk is gone from active context and the running summary never reflects it.

**Why it matters.** Across a long session the bot silently loses long-term situational awareness while `turns[]` keeps rolling forward. With slow / flaky LLMs the timeout fires regularly and memory effectively stops growing, making `save()`d `memory.json` snapshots stale and self-prompt continuity poor.

**Suggested fix.** On failure, either (a) prepend the dropped chunk back into `turns` to retry next eviction, or (b) fall back to a deterministic concatenation summary (e.g. previous memory + truncated chunk text) so memory still advances. Also clamp `pending_summary` so two failures in a row don't double-evict.

**Verify.** Add `history.summary_timeout_preserves_continuity`: stub `promptMemSaving` to reject, drive `add()` past `max_messages` twice, assert `memory` has changed (or the chunk is recoverable). Watch for repeated `memory.summary.failure` events with no following `memory.summary.end`.

### F-004 — `replaceStrings` rebuilds `$STATS`/`$INVENTORY`/`$EXAMPLES` on every retry

| Field | Value |
| ----- | ----- |
| Severity | **major-revision** |
| Type | perf |
| Effort | 1-4h |
| Where | `src/models/prompter.js:218-292` |

**Symptom.** `promptConvo` loops up to 3 times for hallucination retries and calls `replaceStrings(prompt, messages, this.convo_examples)` inside the loop. Each retry re-runs `!stats`, `!entities`, `!nearbyBlocks`, `!inventory` and re-runs example retrieval (including a fresh embedding query).

**Why it matters.** Every retry pays the cost of re-embedding the latest intent and re-querying the bot world for stats, entities, nearby blocks, and inventory. A 3× retry burst hits the embedding API and bot APIs three times for content that does not change between retries — adding latency and embedding cost during exactly the situations (hallucinations) where the bot is already misbehaving.

**Suggested fix.** Compute `$STATS`/`$INVENTORY`/`$EXAMPLES` once before the retry loop (or cache them keyed on `current_msg_time`) and only re-render template substitution on retries. Only `$ACTION`/`$SELF_PROMPT` genuinely need re-evaluation if state can change.

**Verify.** Spy on `getCommand('!stats').perform` and on `convo_examples.getRelevant`: a `promptConvo` with two hallucinated retries should call each at most once. Transcript should show fewer `model.request` entries with redundant stats blocks.

### F-005 — `TranscriptLogger.record` uses `appendFileSync` on every event (hot-path block)

| Field | Value |
| ----- | ----- |
| Severity | **major-revision** |
| Type | perf |
| Effort | 1-4h |
| Where | `src/agent/transcript_logger.js:31` (called from many sites in `src/models/prompter.js:228-397`, `src/agent/agent.js`, `commands/index.js:215-253`, `action_manager.js`, `history.js`) |

**Symptom.** `record()` calls `fs.appendFileSync` for every event. Every chat in/out, `model.request/response/failure`, `command.parse/start/end/failure`, `action.start/end`, `memory.*`, and the new `objective.*` events trigger a synchronous disk write. Many of these happen on the bot's tick path.

**Why it matters.** On Windows or a slow disk this stalls the bot loop ~1–10 ms per event, and the bot emits dozens of events per turn. Worse, errors during the write print to `console.error` and the bot keeps going as if logging worked — a full-disk condition becomes invisible. The whole point of transcripts is observability; they shouldn't change runtime behavior.

**Suggested fix.** Buffer entries in memory and flush asynchronously: a queue + `fs.promises.appendFile` triggered on a 100 ms interval or every N entries, with a final flush in `agent.cleanKill`. Alternatively switch to `fs.createWriteStream` opened once per session and `.write()` per event (Node buffers internally).

**Verify.** Benchmark: log 10 k events; wall-clock should drop under 250 ms after the change. Add a `transcript.flush.failure` event and look for it in the JSONL on a `chmod 000` test directory.

### F-006 — Embedding cache keyed by normalized intent collides across examples

| Field | Value |
| ----- | ----- |
| Severity | **major-revision** |
| Type | correctness |
| Effort | 1-2d |
| Where | `src/utils/examples.js:99-115,139-151` |

**Symptom.** `load()` stores embeddings keyed by `exampleIntentText(example)`, which after `normalizeIntentText` collapses many surface forms ("please mine 3 wood", "hey can you mine wood?") to identical strings. When two examples share an intent string, the second `load` overwrites the first's embedding, and `embeddingScore` returns the same similarity for both at query time — ranking degenerates to the assistant-output word-overlap tiebreaker.

**Why it matters.** The supposed embedding-based ranking silently becomes word-overlap ranking for any duplicate-intent examples — exactly the case for `conversation_examples` bundles that intentionally repeat phrasings with different responses. The reworked retrieval reliably selects the wrong example whenever intents collide.

**Suggested fix.** Key embeddings by example index (or a stable hash of the full example payload) instead of by normalized intent text — `this.embeddings[i] = embedding` during load, lookup by index in `embeddingScore`. Alternatively, append an index suffix to disambiguate.

**Verify.** Unit test: load two examples with identical user content but different assistant outputs; stub the embedding model to return distinct vectors; confirm `getRelevant` ranks them in the order matching distinct embedding lookups.

### F-007 — `goToPositionChunked` anchors waypoints at current Y, fails on long vertical journeys

| Field | Value |
| ----- | ----- |
| Severity | **major-revision** |
| Type | design |
| Effort | 1-2d |
| Where | `src/agent/library/skills.js:1681-1700` (the chunk waypoint computation) |

**Symptom.** Each waypoint is `(here.x + dx*scale, here.y, here.z + dz*scale)` then `GoalNear(wp.x, wp.y, wp.z, 5)`. When start and target are at very different Y (e.g. surface bot returning to a Y=-50 mining entry), every intermediate keeps the bot's current Y rather than interpolating toward the destination.

**Why it matters.** The chunk loop runs up to 50 chunks each finishing at a Y that doesn't approach the chest. `mineOre`'s deposit cycle then either hits the safety cap or arrives at chunked surface positions never reaching the chest, which is reported as "Could not reach home chest" and aborts with `deposit_failed`.

**Suggested fix.** Interpolate Y proportionally to planar progress, OR widen `GoalNear` radius for intermediates (e.g. 16) so the pathfinder picks elevation. Treat the final hop separately with the strict `min_distance`.

**Verify.** Bot at Y=70, target at Y=-50 with chunked nav — expect "Within threshold of target" before the 50-chunk safety cap and final `goToPosition` success.

| Field | Value |
| ----- | ----- |
| Severity | small-fix |
| Type | bug-risk |
