## Findings

### F-001 - Stuck detection records a blocker but leaves the action running

| Field | Value |
| ----- | ----- |
| Severity | **major-revision** |
| Type | bug-risk |
| Effort | 1-4h |
| Where | `src/agent/action_manager.js:126-188` |

**Symptom.** The stuck watcher sets `task_ledger` to blocked, chats "Blocked", and records `action.stuck`, but it never interrupts `actionFn`, stops pathfinder, clears `executing`, or returns control to the agent loop.

**Why it matters.** Several actions are launched with `timeout: -1`. If one of those stops making progress, the bot can truthfully detect that it is stuck while remaining in the same running action that caused the stuck condition.

**Suggested fix.** Decide whether `action.stuck` is advisory or terminal. For terminal stuck states, call `requestInterrupt()`, cancel resume, stop pathfinder/collectBlock/pvp, and return a structured `ERR_ACTION_STUCK` result to history. For advisory states, do not mark the task ledger blocked yet.

**Verify.** Add an `ActionManager` test with a fake bot whose position and inventory never change, a low `action_stuck_after_ms`, and a long action promise. Assert that the action returns or is interrupted with a stable stuck result.

### F-002 - Generic action wrapper turns failed skills into OK-looking results

| Field | Value |
| ----- | ----- |
| Severity | **major-revision** |
| Type | correctness |
| Effort | 1-4h |
| Where | `src/agent/commands/actions.js:29-49` |

**Symptom.** `runAsAction` returns `explicitReturn` for any non-null value, including `false`, and otherwise falls back to free-text `code_return.message`. `normalizeCommandResult(false)` becomes raw text `"false"` and is classified as `OK`.

**Why it matters.** Many simple actions (`!goToPlayer`, `!goToCoordinates`, `!craftRecipe`, `!prepareMiningRun`) call skill functions without wrapping success/failure in structured results. If a skill returns false or only logs failure text, the model may see an `OK:` command result and repeat the same trivial action instead of recovering.

**Suggested fix.** Make `runAsAction` normalize booleans and missing output explicitly: `true -> OK`, `false -> ERR_ACTION_FAILED`, interrupted -> `ERR_INTERRUPTED`, timeout -> `ERR_TIMEOUT`. Then migrate high-use skills to return `objectiveResult` or throw typed errors.

**Verify.** Add a command test with a temporary action whose skill returns `false`; assert `executeCommand` returns `ok: false` and a non-OK code.

### F-003 - Forced user commands bypass conversational history

| Field | Value |
| ----- | ----- |
| Severity | **major-revision** |
| Type | design |
| Effort | 1-4h |
| Where | `src/agent/agent.js:487-525` |

**Symptom.** Direct user commands are executed and routed back immediately, but the user command and command result are not added to `History` except for `!newAction`. Session memory records only a compact last-command summary.

**Why it matters.** Direct commands are often corrections: save this chest, import this waypoint, show task status, stop doing that. The next model prompt may not contain the full instruction/result pair, so the bot has durable side effects but a weak conversational explanation of why they happened.

**Suggested fix.** Add a compact forced-command turn pair to history: user command text plus rendered command result, capped like normal command output. Keep the current fast path, but preserve enough context for the next model decision.

**Verify.** Extend `test/agent_handle_message.test.js` so a forced `!rememberHere` or `!taskStatus` appears in subsequent `history.getHistory()` with its rendered result.

### F-004 - Memory summarization still blocks the prompt path

| Field | Value |
| ----- | ----- |
| Severity | **major-revision** |
| Type | perf |
| Effort | 1-2d |
| Where | `src/agent/history.js:153-184` |

**Symptom.** `History.add` starts a pending summary when max history is reached, and `History.save` immediately calls `flushPendingSummary()`. `Agent._handleMessage` saves before prompting, so a normal user message can wait on memory summarization before the model even starts.

**Why it matters.** This can look exactly like the bot getting stuck on trivial work: the input is accepted, but the main loop waits on a secondary summarization model call or its timeout. The default timeout guard helps, but it still puts memory maintenance on the critical response path.

**Suggested fix.** Split "save current state" from "wait for summary". Persist a snapshot that includes pending chunks, or leave evicted turns visible until the summary finishes. Only flush synchronously on shutdown or explicit memory commands.

**Verify.** Add a test that forces eviction with a never-resolving `promptMemSaving`, calls `handleMessage`, and asserts the chat prompt is attempted without waiting for the memory timeout.

### F-005 - The repo has multiple competing progress memories

| Field | Value |
| ----- | ----- |
| Severity | **major-revision** |
| Type | design |
| Effort | >1wk |
| Where | `src/models/prompter.js:254-277` |

**Symptom.** `$MEMORY` now concatenates text memory, task ledger summary, session memory, and ranked `MemoryBank` facts. Mining also writes both `ObjectiveStack` and `TaskLedger`, while command execution updates `session_memory` separately.

**Why it matters.** There is not one authoritative answer to "what am I doing, what failed, and what should happen next?" The model has to reconcile overlapping summaries, stale command results, objective state, task-ledger state, and durable world facts inside prompt text.

**Suggested fix.** Pick a single active-task state machine as the source of truth, probably `TaskLedger` plus typed command results. Make `ObjectiveStack` either an implementation detail under that state machine or remove it from prompt-facing memory. Keep `MemoryBank` for durable world facts only.

**Verify.** Create end-to-end fixtures for "mine ore", "blocked missing supplies", "user changes goal", and "restart during active task". Each should produce one unambiguous prompt-facing state summary.

### F-006 - Multiple commands from one model turn run without feedback

| Field | Value |
| ----- | ----- |
| Severity | **major-revision** |
| Type | design |
| Effort | 1-2d |
| Where | `src/agent/agent.js:578-648` |

**Symptom.** The prompt docs tell the model to use at most one command and wait for the result, but the loop extracts and executes every command in one response. The second command executes before the model sees the first command result.

**Why it matters.** For query-only chains this is convenient. For action commands, it removes the feedback barrier that makes the agent loop controllable. A single bad generation can queue stale follow-up actions against a world state that has already changed.

**Suggested fix.** Enforce one action command per model turn. Optionally allow multiple read-only queries, but stop before a second action and feed the first result back through the model.

**Verify.** Update the existing multi-command tests to distinguish query chaining from action chaining. Assert that two actions in one response execute only the first action before re-prompting.

### F-007 - Blocked and interrupted task-ledger states have no lifecycle

| Field | Value |
| ----- | ----- |
| Severity | **major-revision** |
| Type | design |
| Effort | 1-4h |
| Where | `src/agent/task_ledger.js:5-6,100-140,172-191` |

**Symptom.** `completed` and `failed` archive, but `blocked` and `interrupted` remain current. `load()` marks only `pending`, `running`, and `active` as interrupted; `start()` archives only terminal states before overwriting current.

**Why it matters.** A blocked task can persist indefinitely in prompt memory, and a new task can overwrite it without putting the old blocked state in history. That makes task state both sticky and lossy depending on which path happens next.

**Suggested fix.** Define explicit task lifecycle states: active, blocked-awaiting-user, abandoned, failed, completed. Add commands or command-result transitions for resume/abandon, and archive superseded blocked/interrupted tasks with a reason.

**Verify.** Add tests for loading a blocked task, starting a different task while blocked, and abandoning/resuming a blocked task. Assert prompt summaries and ledger history match the chosen lifecycle.

### F-008 - Housekeeping prompts use the main chat model and shared cooldown

| Field | Value |
| ----- | ----- |
| Severity | small-fix |
| Type | cost |
| Effort | 1-4h |
| Where | `src/models/prompter.js:509-558` |

**Symptom.** `promptMemSaving` and `promptShouldRespondToBot` call `checkCooldown()` and use `this.chat_model`. They share the same throttle and model path as actual conversation reasoning.

**Why it matters.** Memory summarization and bot-response classification are housekeeping. Routing them through the main model can add latency and cost, and the shared cooldown can delay the next real user response.

**Suggested fix.** Add a `utility_model` or `cheap_model` profile slot with a fallback to chat. Give utility prompts their own cooldown, or no cooldown when the provider already rate-limits.

**Verify.** Add a prompter unit test that stubs chat and utility models and asserts memory saving and bot-responder calls use the utility model without changing `last_prompt_time` for chat.

**Why it matters.** This is not part of the bot architecture; it is local investigation instrumentation committed into a lifecycle path. It adds hidden I/O on every shutdown and leaks stack/message details to any process listening on that port.

## Architecture drift notes

- The baked architecture reference says responses containing a command are truncated to the first command. Current `Agent._handleMessage` executes every parsed command in a model response. Either the reference should be updated, or the code should be changed back to one command per model turn.
- The architecture index still presents memory as recent turns, text summary, and `MemoryBank`. Current behavior also depends on `session_memory`, `TaskLedger`, route memory, storage memory, JourneyMap imports, and world identity. The docs should name these as first-class state surfaces if they remain.
