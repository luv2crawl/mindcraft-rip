# Mindcraft Code Review: Memory System

- Date (UTC): 2026-05-02 16:46:58
- Branch: improvements
- Scope: focused memory-system review
- Files inspected: 11
- Hot spots inspected: History persistence/summarization, MemoryBank, memory commands, prompt injection

## Summary

The memory system has a real persistence hole: direct user commands that mutate structured memory return before `history.save()` runs. Model-emitted commands usually save after command processing, so this failure is easy to miss in normal chat tests. This directly matches the current-session symptom where imported/base/location memory appears not to be populated or saved.

I also found design gaps that make the bot appear forgetful even when memory was saved: structured memory is not rendered into the main prompt, `!savedPlaces` only exposes one namespace, and `MemoryBank` has no dirty/persist contract.

## Findings

### 1. Major - Forced memory commands return before persisting `memory_bank`

- Type: bug-risk, correctness
- Effort: small-fix
- Files: `src/agent/agent.js:335`, `src/agent/commands/actions.js:337`, `src/agent/commands/actions.js:547`, `src/agent/commands/actions.js:740`

Direct user commands are handled in the forced-command path in `Agent.handleMessage`. After `executeCommand(this, message)`, the method records transcript metadata and returns without calling `history.save()`. Memory-mutating commands such as `!importJourneyMapLocation`, `!rememberHere`, and `!setHomeChest` write only to `agent.memory_bank` in RAM.

Model-emitted commands are different: after the response command loop, `history.save()` runs at `src/agent/agent.js:480`. That means structured memory persistence depends on whether the command came from the user directly or from the model, which is surprising and fragile.

Impact: a user can import a JourneyMap base, save a home chest, or remember a place, get a success response, restart the bot, and lose that structured memory.

Recommended fix: save after successful forced command execution. The minimal change is to call `await this.history.save()` before returning from the forced-command block. A stronger design is to add memory-command metadata or a MemoryBank dirty flag, but the forced path should still flush before return.

Suggested regression test: execute a forced `!importJourneyMapLocation("[x:10, y:64, z:-20, dim:0, name:MAIN_BASE]")`, instantiate a fresh agent/history, and assert the waypoint survives reload.

### 2. Major - `MemoryBank` has no dirty flag or persistence hook

- Type: design, bug-risk
- Effort: major-revision
- Files: `src/agent/memory_bank.js:68`, `src/agent/history.js:184`

`MemoryBank.remember()` mutates the typed namespace and returns the stored value, but it does not mark itself dirty, emit a change event, or know how to request persistence. Persistence happens only when some caller elsewhere happens to run `History.save()`.

This makes every new structured-memory feature responsible for knowing the save lifecycle. The current forced-command bug is one manifestation, but route recording, storage indexing, JourneyMap sync, and future memory writes are all exposed to the same class of mistake.

Recommended fix: give `MemoryBank` a dirty contract:

- `remember()` / `loadJson()` can set or clear `dirty`.
- `Agent` or `History` can flush dirty memory at the end of command execution, on shutdown, and after periodic route/storage updates.
- Tests should assert command execution triggers a save when `memory_bank.dirty` is true.

### 3. Major - `memory.json` writes are not atomic, and load does not recover corrupt files

- Type: bug-risk, reliability
- Effort: small-fix
- Files: `src/agent/history.js:175`, `src/agent/history.js:186`, `src/agent/history.js:203`, `src/agent/history.js:209`

`History.save()` writes the entire memory file directly with `writeFileSync(this.memory_fp, JSON.stringify(...))`. If the process exits during write, or the filesystem produces a partial write, `History.load()` later calls `JSON.parse(readFileSync(...))` on the final file with no recovery path.

Impact: one interrupted write can corrupt `bots/<name>/memory.json` and break loading for that bot. This matters more now because structured memory and chat memory share the same file.

Recommended fix: write to a sibling temp file, fsync if practical, then rename over `memory.json`. On load failure, move the corrupt file to a timestamped backup, initialize a clean memory state, and emit a transcript/load warning.

Suggested regression test: create an invalid `memory.json`, call `History.load()`, and assert the agent starts with empty memory instead of throwing.

### 4. Minor - Structured memory is not surfaced in the main prompt

- Type: design, usability
- Effort: small-fix
- Files: `src/models/prompter.js:176`, `profiles/defaults/_default.json`

Prompt replacement injects only `agent.history.memory` when `$MEMORY` is present. The typed `memory_bank` is saved separately and is only accessible if the model knows to call query commands such as `!journeyMapWaypoints`. The main conversation prompt does not include even a compact list of saved bases, waypoints, storage labels, or routes.

Impact: after a successful structured-memory write, the model may still behave as if it forgot the data unless the right query command appears in context or examples. This is especially visible for planning flows such as mining runs, where the bot should default to the closest designated base.

Recommended fix: add a compact structured-memory rendering path. For example, append a short "Structured memory" section to `$MEMORY`, or introduce `$STRUCTURED_MEMORY` in the default conversation prompt. Keep it bounded: counts plus top relevant names/coordinates are enough.

Suggested regression test: seed `memory_bank.journeymap.waypoints.MAIN_BASE`, render the conversation prompt, and assert `MAIN_BASE` appears in the prompt.

### 5. Minor - `!savedPlaces` hides most structured memory

- Type: correctness, usability
- Effort: small-fix
- Files: `src/agent/commands/queries.js:243`

`!savedPlaces` returns only `agent.memory_bank.getKeys()`, which is the legacy `places` namespace. It does not show JourneyMap waypoints, storage indexes, routes, observations, or pending route issues.

Impact: both the user and the model can ask for saved locations and get an apparently empty result even when structured waypoints or storage memory exist. This makes the memory system look broken and encourages duplicate imports.

Recommended fix: either expand `!savedPlaces` into a broader memory summary or add a new `!memory` / `!structuredMemory` query command. At minimum, show counts and names for places, JourneyMap waypoints, storage, and routes.

Suggested regression test: seed a waypoint and a storage record, run the query command, and assert both namespaces are visible.

### 6. Minor - Remembered places lose dimension data

- Type: correctness
- Effort: small-fix
- Files: `src/agent/memory_bank.js:57`, `src/agent/memory_bank.js:61`, `src/agent/commands/actions.js:547`, `src/agent/commands/actions.js:740`

`rememberPlace(name, x, y, z)` stores only coordinates. `recallPlace()` returns an `[x, y, z]` tuple, so any future metadata is discarded by that API. JourneyMap waypoints and route records can include dimension, but saved places and `home_chest` cannot.

Impact: location recall can cross dimensions incorrectly. A remembered base or chest in one dimension may be used while the bot is in another dimension.

Recommended fix: extend `rememberPlace` to accept an optional dimension/source object and preserve it in the stored record. Prefer returning the full record from a new API such as `recallPlaceRecord()` while keeping `recallPlace()` for backward compatibility.

## Architecture Drift Notes

- The architecture reference describes `MemoryBank` as a flat key-value store, but the live implementation uses typed namespaces (`places`, `journeymap.waypoints`, `routes`, `storage`, `observations`, `pending`). Update the reference docs so future work does not reintroduce flat-memory assumptions.
- The live command loop can execute multiple model-emitted commands serially, while older architecture notes describe truncation to a first command. That is not the core memory bug here, but it changes where save hooks should live: persistence should be tied to command execution completion, not a single response boundary.

## Test Coverage Gaps

- There is a round-trip test for `History.save()` and `MemoryBank` in `test/situational_memory.test.js`, but it manually calls `history.save()`. It does not cover real command execution paths.
- Add forced-command persistence coverage for `!importJourneyMapLocation`, `!rememberHere`, and `!setHomeChest`.
- Add prompt-rendering coverage for structured memory visibility.
- Add corrupt `memory.json` recovery coverage once atomic save/recovery is implemented.
